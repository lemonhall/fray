# FRAY 架构说明（写给架构师）

这份文档回答三个问题：**前端负责什么、后端负责什么、一局游戏到底发生了哪些请求。**

如果你只想看代码，先看 `sim/`——它是整个项目的重心。

---

## 一、一句话架构

> **一份确定性内核，跑在两个地方：Durable Object 里它是权威，浏览器里它只用来预测自己的位移。**

```
 ┌───────────────────────── 浏览器 ──────────────────────────┐
 │  UI 层        rooms / roomui / hud / results / showcase    │  纯 DOM
 │  表现层       render / sprites / fx / audio / view         │  canvas 2D
 │  预测层       predict  ← 只预测"我自己"的位移              │
 │  网络层       net + input（25Hz 上行"意图"）               │
 └───────────────────────┬───────────────────────────────────┘
                         │ WebSocket（JSON）
 ┌───────────────────────▼───────────────────────────────────┐
 │  Worker（无状态，可被复制到任何边缘节点）                  │
 │    认租户 → 认令牌 → 路由到对的 DO → 补 CORS               │
 │    ★ 这里没有任何游戏判定                                  │
 └───────┬───────────────────────────────┬───────────────────┘
         │                               │
 ┌───────▼────────────┐        ┌─────────▼──────────┐
 │ Room DO（一个房间）│        │ Lobby DO（一个租户）│
 │  名册 / 开局 / 推进│        │  房间目录（单点强一致）│
 │  可见性过滤         │        └─────────┬──────────┘
 │  ★ 唯一的权威       │                  │
 └───────┬────────────┘                  │
         │                               │
 ┌───────▼───────────────────────────────▼───────────────────┐
 │  D1：租户表 / 战绩表（排行榜、最近对局）                   │
 └───────────────────────────────────────────────────────────┘
```

共享内核 `sim/` 的 15 个模块：地图、角色、战斗、子弹、AI、流程、世界推进、线格式。
**服务端 `import "../sim/x.mjs"`，浏览器 `import "/sim/x.mjs"`——同一份文件。**
`tools/build.mjs` 只做一件事：把它复制进 `web/sim/`，再用一个 30 行的循环校验
每个引用都真的存在。不引入打包器，因为这里没有依赖、没有转译需求，产物就是你写的
那些文件，DevTools 里能一行行对上。

## 二、职责边界（谁该管什么）

### 前端负责

| 职责 | 具体是什么 | 代码 |
|---|---|---|
| 采集**意图** | 键位、准星、开火键、一次性动作 → 一帧 25Hz 的 `in` | `js/input.mjs` |
| **命令时间线** | 把"按哪个方向走了几格"打成带序号的命令；方向一变立刻收尾 | `js/cmd.mjs` |
| **只**预测我自己 | 用共享内核的 `applyMove` 跑自己的位移；快照回来时从 ack 点重放未确认命令 | `js/predict.mjs` + `sim/replay.mjs` |
| 插值渲染 | 快照环形缓冲 + 90ms 延迟，把 20Hz 快照画成不抖的 60fps | `js/view.mjs` |
| 表现 | 精灵、粒子、跳字、光束、音效、屏幕震动、小地图、HUD | `render/sprites/fx/audio/hud` |
| 界面状态 | 四个屏（房间浏览器 / 候场 / 竞技场 / 结算）的切换 | `js/app.mjs` |
| 房间运维动作 | 建房、加入、加机器人、开始、三选一——**都只是"发一条消息"** | `rooms/roomui/net` |

前端**不做**的事：判定命中、判定死亡、判定谁赢、决定谁能改房间配置、决定我看得见谁。
一句话概括边界——**前端可以撒谎，但撒谎没用**，因为它上报的从来不是结论，只是意图。

### 后端负责

| 职责 | 具体是什么 | 代码 |
|---|---|---|
| 身份 | 游客令牌签发与验签（无状态 HMAC） | `src/auth.mjs` |
| 租户 | 租户注册、规则（人数上限、房间上限、是否允许游客） | `src/tenants.mjs` |
| 目录 | 房间一览（单点强一致）、建房、快速匹配 | `src/lobby.mjs` |
| 名册与权限 | 谁在房里、谁是房主、能放几个机器人、能不能开局 | `src/room-state.mjs` |
| 对局生命周期 | 名册 → 场上实体；中途进出；结算与重开 | `src/room-match.mjs` |
| **权威模拟** | 60Hz 定步推进、AI 决策、命中判定、缩圈、胜负 | `sim/*` |
| **可见性过滤** | 每个客户端收到的是"以他的视角裁剪过"的快照 | `sim/wire.mjs` |
| 落库 | 战绩与排行榜 | `src/results.mjs` |

## 三、一局比赛的完整时序（从打开 URL 到打完）

```
浏览器                                           Worker / DO
  │ ① POST /v1/neon/guest {name}                    │
  ├────────────────────────────────────────────────►│  签一张游客令牌
  │ ② GET /v1/neon/rooms                            │
  ├────────────────────────────────────────────────►│  Lobby DO.list()
  │ ③ GET /v1/neon/leaderboard?limit=8              │
  │ ④ GET /v1/neon/matches?limit=8                  │  ②③④ 并行，每 4 秒重来一次
  │                                                 │
  │ ⑤ POST /v1/neon/rooms {name,mode,difficulty,bots}│
  ├────────────────────────────────────────────────►│  Lobby.create() → Room DO.init()
  │◄────────────── 201 {roomId:"YRC7J5"} ───────────│
  │                                                 │
  │ ⑥ WS  /v1/neon/rooms/YRC7J5/socket?token=...    │
  ├────────────────────────────────────────────────►│  Room 验令牌，入名册
  │◄──── {t:"hello", you, room} ────────────────────│  名册首帧
  │── {t:"hero", i:0} / {t:"gadget", id} ──────────►│  我的选择
  │◄──── {t:"room"} ×N（任何名册变化都会广播）──────│
  │                                                 │
  │   （第二个真人加入 → 同样的 ⑥；房主加机器人）   │
  │── {t:"bots", n:5} ─────────────────────────────►│  非房主发这条会被直接丢弃
  │                                                 │
  │── {t:"start"} ─────────────────────────────────►│  纯函数 startCheck() 先过门槛
  │◄──── {t:"begin"}  {t:"map"}  {t:"s"(第 0 帧)} ──│  ★ 顺序不能反
  │                                                 │
  │══ 之后每一帧都是这个循环 ══                     │
  │── {t:"in", k,a,f,act,r} ×25/秒 ────────────────►│  补算到"现在"（60Hz 定步）
  │                                                 │  AI 决策 / 子弹 / 伤害 / 缩圈 / 得分
  │◄──── {t:"s"} ×20/秒（50ms 节流，逐人裁剪）──────│
  │   插值 → 渲染 → HUD                              │
  │                                                 │
  │◄──── {t:"over", results} ───────────────────────│  比分到线 / 只剩一人
  │── {t:"reset"}（房主）──────────────────────────►│  回到 staging，重开一局
```

### 每一跳都在干什么

1. **拿令牌**：打开页面唯一必须先完成的事。后面所有请求都挂在它身上。
2. **看房间**：三个只读请求并行，4 秒一轮。
3. **建房**：服务端用租户规则夹一遍参数，在 Lobby 里占一个房间号，再把房间 DO 初始化。
4. **连 WebSocket**：握手成功即入名册；`hello` 是"我看到的房间"的第一帧。
5. **候场期间的 `room` 广播**：名册、机器人数量、模式、阶段。房主与普通玩家收到的是
   **同一份数据**，界面根据 `you.host` 决定按钮可不可点——但真正的拒绝发生在服务端
   （`isHost()`），界面永远不是安全边界。
6. **`start`**：服务端生成 `matchSeed`（这一局的身份）、重铺地图、按"前两个真人必分
   对立两队"排兵，然后按 `begin → map → 第一帧快照` 的顺序下发。
7. **对局循环**：客户端只报意图；服务端算一切；快照逐人裁剪后下发。
8. **`over`**：结算算在服务端，客户端只显示。

## 四、几个"为什么这么设计"

### 1. Room DO 里没有常驻定时器

每当任意客户端发来一条消息，就把模拟**补算**到墙上时间（60Hz 定步，带补算上限），
再按 50ms 节流窗口决定是否广播。于是：

* 不需要长跑定时任务 → 账单与生命周期都简单，免费计划也够用；
* CPU 只在实际有人玩的时候烧；
* 代价是**所有客户端同时掉线时世界会停**。所以有一个 5 秒的 alarm 兜底做清理、
  回收目录、以及"心跳续命"。

### 2. 可见性即反作弊

草丛里、墙后面、风暴外看不见的敌人，**根本不进你的快照**。这不是"前端别画"，
是"服务端不发"。做外挂的人可以先改 JS，但他改不了自己收不到的字节。

局部战争迷雾的代价是服务端要为每个客户端单独编码一份快照（6 人 = 6 次编码/帧），
这是这套架构唯一明显比"广播同一份"更贵的地方，换来的是根本性的信息隔离。

### 3. 只用本地预测"我自己"的位移

`sim/input.mjs` 里的 `applyMove` 是纯函数（只依赖网格、箱子、移速），所以浏览器和
服务端算出同一个结果。子弹、伤害、死亡一概不预测——否则就会出现"我这边打死了、
别人那边还活着"这种最能破坏信任的画面。

### 3.1 为什么移动不会被拽回去（输入命令时间线 + ack 重放）

第一版上线的当天就收到反馈：「往前走了一段路，又跳回了一小段」。这就是
**rubber-banding**：客户端预测和服务端权威各走各的，对账那一刻把人往回拉。

它在本地永远测不出来。用 `tools/latency-proxy.mjs` 注入"100ms 单向 + 30ms 抖动 +
周期拥塞"之后，`tools/netcode-probe.mjs` 量到的数字是：单帧往回跳 **288px**。
根因有两处，都不是"网络不好"，是代码把自己的时间丢了：

* **服务端补算丢时间**：消息断流超过 500ms 时，补算直接把积压的时间**扔掉**
  （`base = now`）。服务端于是比客户端预测走得慢，误差越积越大，直到撞上客户端
  的硬吸附阈值（70px）被"啪"地拽回去。
* **限流挂错了对象**：漏桶挂在**房间**上，6 人 × 25Hz = 150 条/秒共用 70 条/秒的
  预算，等于全员被自己的房间限流，输入成片地丢。

修法是换一条对账规矩：**不比"现在的两个坐标"，而是回到时间线上对**。

```
客户端                                    服务端
  │ 命令 41/42/43（带序号、方向、格数）──►│  逐格消耗，走完一条才 ack
  │                                        │  ① 消耗命令 41 → ack=41, 记下那时的坐标
  │◄─── 快照 { ak:41, ax, ay } ────────────│  ② 广播照样每 50ms 一次
  │ 丢掉 sq>41 以外的（没有），从 (ax,ay)  │
  │ 重放还没被确认的命令 → 正常情况下     │
  │ 重放结果和本机预测**逐像素相同**       │
```

关键性质：只要两端跑的是同一个 `applyMove`，重放结果就和本机预测一致，**对账的
位移改动量是 0，画面上什么都不发生**。只有当服务端真干了客户端算不到的事
（被击退、闪避、破墙）时，重放结果才会不一样——那才是"该纠正的分歧"。
两个细节值得记住：

* **一条命令只有一个方向**，所以方向一变就立刻把上一条收尾发走，而不是等下一个
  40ms 节拍。代价是方向切换时多几条消息，换来的是"重放路径和本机预测一致"。
* **第一格就把命令挂进待确认列表**（`noteTick`），不能等到发送。快照随时可能在
  两条命令之间落地；正在走的那条如果还没进列表，对账时就会凭空少走几格。
* 差异小于 0.5px **直接认账**、不做平滑——那是方向量化成 1/16 之后的浮点舍入，
  不是分歧；把它也拿去做平滑，就会被乘成反方向的抖动。

服务端那边同时把 `MAX_CATCHUP_TICKS` 从 30 提到 240（4 秒），漏桶从"按房间"
改成"按连接"。复测：**最大单帧回退 288px → 0.1px**（一像素的十分之一，屏幕上
不存在），理想轨迹偏离 <1.5px。

> 这两个诊断工具值得单独记一笔：`latency-proxy.mjs` 是一个纯 TCP 延迟注射器
> （基线 + 抖动 + 周期拥塞窗口），`netcode-probe.mjs` 用 Playwright + 本机 Chrome
> 挂在这个代理后面逐帧采样本机预测坐标。它们不碰线上账号、不产生账单，却让
> "手感"这件最主观的事第一次变成了可测量、可回归的数字——本地 localhost 上这个
> 数字恒等于 0，只有把真实延迟放进来，这一类 bug 才有出生地。

### 4. JSON 而不是二进制

省下 60% 字节的东西，代价是没人能在 DevTools 里读懂一帧。这个项目的读者首先是
架构师，所以字段名都短到一眼扫完，含义在 `sim/wire.mjs` 里写死。

### 5. 同一份内核跑两边

地图生成、移动、可见性判定这些逻辑如果前后端各写一份，早晚会漂移成两个世界。
把 `sim/` 做成纯 ES 模块、两边直接 import，是"零依赖、可测试、可复刻"三个目标的
公共解。测试也受益：`tests/sim-smoke.test.mjs` 直接对着内核断言，不需要起 workerd。

### 6. 一张令牌 = 一个玩家：身份必须"最后一次说了算"

游客令牌里**带着玩家 id**，所以"改昵称"这件事在协议上就等于"重新签一张令牌"。
而浏览器里同时可能有好几次签发在飞（进站初始化、改名、建房），HTTP 的返回顺序
**不保证**和发出顺序一致——旧的那张晚到一步，就会把 `S.token` 覆盖掉。如果建房
已经用旧令牌提交过了，结果就是：**房间是你的，房主却不是你**。

修法是把身份收进一道闸门（`web/js/identity.mjs`），三条规矩：

* `sign()` 只让**最新那次**的结果落到状态里，过期的结果直接丢；
* `ensure()` 让"建房 / 快速匹配 / 进房"这类动作先等身份落定，别自己猜现在手上是哪张；
* 改名做 400ms 去抖，而且只在大厅里重签——对局中重签等于把"我"换成另一个玩家。

这类 bug 值得记一笔：它在本地（毫秒级链路上）跑一百遍都未必复现，一上跨境链路
（几百毫秒 + 抖动）就稳定出鬼。看代码时它完全"没问题"，只有把真实网络延迟放进来
才会露头——`tests/identity.test.mjs` 用两个可控时序的假签发把它钉住了。

## 五、多租户

一个 Cloudflare 账号、一个 Worker、一份 D1，可以运营多个在线游戏：

* **租户是 URL 的第一段**：`/v1/{tenant}/...`，前端可以 `?tenant=` 切换；
* **DO 的名字带租户**：`env.ROOM.getByName(\`${tenantId}:${roomId}\`)`，
  于是 A 游戏的房间和 B 游戏的房间天然是两个宇宙，不存在"串房"；
* **每个租户一份规则**：人数上限、房间上限、是否允许游客、是否允许机器人；
* **目录也是按租户单点**：`LOBBY.getByName(tenantId)`；
* **D1 的每张表都带 `tenant_id`**，排行榜/战绩天然隔离。

注册一个租户就是在管理面上调一次：

```powershell
curl.exe -X POST https://<worker>/v1/tenants -H "authorization: Bearer $env:ADMIN_KEY" `
  -H "content-type: application/json" -d '{"id":"neon","displayName":"霓虹前线"}'
```

## 六、想接自己的东西，接哪里

| 想做的事 | 动哪里 |
|---|---|
| 换前端（Godot / Unity / 原生 App） | 只实现 `docs/protocol.md` 里的 HTTP + WS，`sim/` 可以直接复用成客户端预测 |
| 接自己的账号 | 用 `POST /v1/{tenant}/sessions`，把内部 `playerId` 换成同一张令牌 |
| 加一张新地图 | `sim/map.mjs` 的生成函数（它是种子化的，服务端与客户端会得到同一张） |
| 加一种新玩法 | `sim/data.mjs` 的 `MODES` + `sim/flow.mjs` 的收局条件 |
| 加一种新强化 | `sim/data.mjs` 的 `PERKS` + `sim/actor.mjs` 的 `applyPerk` |
| 换存储 | `src/results.mjs`（战绩）与 `src/tenants.mjs`（租户）是唯一的两个数据库入口 |
